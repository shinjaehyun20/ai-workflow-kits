# 쉬운거: AI에게 작은 동료를 입히는 일

AI 도구를 매일 쓰다 보면, 어느 순간 기능보다 분위기가 먼저 눈에 들어온다.

대화창은 늘 비슷하고, 명령은 늘 건조하고, 긴 작업은 자주 끊긴다. 그런데 실제 일은 그렇게 단순하지 않다. 어떤 날은 계속 달려야 하고, 어떤 날은 실패를 인정하고 다시 고쳐야 하고, 어떤 날은 멈춰서 검토해야 한다. 그래서 작은 companion을 만들기로 했다. 단순한 장식이 아니라, 내가 어떤 방식으로 일하고 싶은지를 계속 떠올리게 해 주는 작은 기준점이다.

이 글은 그 companion을 만든 기록이다. 핵심은 이미지 생성이 아니다. 예쁜 캐릭터 하나를 뽑는 데서 끝내지 않고, 실제 AI 작업 환경에 넣을 수 있는 작은 패키지로 만드는 과정이다.

## 시작은 "나를 닮은 pet"이었다

처음 요청은 단순했다. AI 작업 환경에서 쓸 custom pet을 만들고 싶었다.

하지만 바로 이미지를 만들지 않았다. 먼저 이 companion이 어떤 역할을 해야 하는지 정했다. 귀여운 캐릭터로 끝나면 금방 질린다. 반대로 너무 상징적이면 실제 작업 화면에서 부담스럽다. 그래서 방향을 이렇게 잡았다.

```text
조용한 실행형 동료
범위를 지켜 주는 보호자
검증을 잊지 않게 하는 companion
```

시각 키워드는 fox, magpie, fairy familiar, utility harness 쪽으로 잡았다. 여우처럼 빠르고, 까치처럼 예민하게 주워 담고, 요정 같은 비현실감을 조금 남기되, 실무 도구 옆에 있어도 어색하지 않은 쪽이다.

이름은 `Nori`로 정했다.

이름을 붙이는 순간부터 결과물은 "이미지"가 아니라 "정체성을 가진 작업 자산"이 된다. 이 차이가 중요했다.

## 한 장의 그림으로는 부족했다

AI companion은 한 장짜리 프로필 이미지가 아니다. 작업 중에는 여러 상태가 생긴다.

- 아무 일도 없을 때
- 오른쪽으로 달릴 때
- 왼쪽으로 달릴 때
- 손을 흔들 때
- 점프할 때
- 실패했을 때
- 기다릴 때
- 실행 중일 때
- 검토 중일 때

그래서 이미지는 상태별로 만들어야 했다. 이번 패키지는 9개의 상태를 기준으로 구성했다.

```text
idle
running-right
running-left
waving
jumping
failed
waiting
running
review
```

이렇게 상태를 나누면 companion은 장식에서 조금 벗어난다. "지금 작업이 어떤 모드인지"를 시각적으로 떠올리게 해 준다. 실패 상태가 있는 것도 중요하다. 실패를 숨기지 않고, 다시 고치는 과정을 workflow의 일부로 보는 태도이기 때문이다.

## 실제 패키지로 만들기

이번 작업의 가장 큰 분기점은 여기였다.

이미지가 마음에 든다고 끝내지 않았다. 실제 앱에서 읽을 수 있는 패키지 형태로 만들어야 했다.

패키지는 크게 두 요소로 나뉜다.

```text
metadata file
spritesheet image
```

metadata에는 companion의 id, 표시 이름, 설명, spritesheet 위치가 들어간다. spritesheet에는 여러 상태의 프레임이 한 장의 이미지 격자 안에 들어간다.

이번 결과물의 구조는 다음 기준으로 검증했다.

| 항목 | 값 |
| --- | --- |
| 전체 이미지 크기 | 1536 x 1872 |
| 격자 | 8 columns x 9 rows |
| 셀 크기 | 192 x 208 |
| 상태 수 | 9 |
| 검증 결과 | structural errors 없음 |

이 숫자들이 맞아야 앱이 companion을 상태별 애니메이션으로 읽을 수 있다. 보기 좋은 이미지여도 격자가 틀리면 실제로 쓸 수 없다.

## "됐다"라고 말하기 전에 확인한 것

AI 작업에서 가장 자주 생기는 실수는 "결과물이 보인다"와 "완료됐다"를 같은 말로 쓰는 것이다.

이번 작업에서는 다음을 확인해야 완료로 봤다.

- companion 이름과 설명이 고정됐는가
- 상태별 프레임이 만들어졌는가
- spritesheet 크기와 셀 크기가 맞는가
- metadata가 spritesheet를 제대로 가리키는가
- validation 결과가 통과했는가
- 실제 앱에서 선택 가능한가

중간에 실패도 있었다. 앱 내부 상태 파일에서 선택된 pet을 직접 바꾸는 명확한 키를 찾지 못했다. 자동 클릭으로 companion을 안정적으로 선택하는 것도 실패했다. 하지만 최종적으로는 앱의 설정 화면에서 직접 선택하는 경로가 확인됐다.

이 실패는 오히려 좋은 기록이다. 자동화가 모든 것을 대신하지 못할 때, 어디까지 자동화했고 어디부터는 수동 검증인지 선을 남겨야 하기 때문이다.

## 이 작업에서 배운 것

작은 companion 하나를 만드는 일도 workflow로 보면 꽤 많은 것이 보인다.

첫째, 컨셉을 먼저 잠가야 한다.
AI 이미지 생성은 방향이 조금만 흔들려도 결과가 금방 다른 캐릭터가 된다. 이름, 역할, 외형 키워드를 먼저 정해야 뒤의 프레임들이 같은 정체성을 유지한다.

둘째, 산출물은 "보이는 결과"와 "쓸 수 있는 결과"가 다르다.
이미지는 예뻐도 패키지 규격이 맞지 않으면 실패다. 반대로 조금 덜 화려해도 구조가 정확하면 다음 개선이 가능하다.

셋째, 실패 상태를 포함해야 한다.
실행 중, 대기 중, 검토 중뿐 아니라 failed 상태를 넣었다. 이건 UI 상태이기도 하지만 작업 철학이기도 하다. 실패는 숨기는 것이 아니라 다시 검증하는 단계다.

넷째, 공개 글과 내부 로그는 다르게 써야 한다.
내부 devlog에는 로컬 경로와 검증 파일 위치가 자세히 남아 있다. 하지만 공개 글에는 그런 정보가 필요 없다. 공개 글에는 흐름, 기준, 재사용 가능한 방식만 남겨야 한다.

## 다른 사람이 따라 한다면

처음부터 이렇게 나누면 된다.

```text
1. companion의 이름과 역할을 정한다.
2. 상태 목록을 정한다.
3. base visual을 만든다.
4. 상태별 프레임을 만든다.
5. spritesheet로 조립한다.
6. metadata를 작성한다.
7. 크기와 상태 매핑을 검증한다.
8. 실제 앱에서 선택 가능한지 확인한다.
```

도구는 달라도 순서는 비슷하다.

중요한 것은 "AI로 이미지를 만들었다"가 아니다. 중요한 것은 그 이미지를 실제 작업 환경에서 다시 쓸 수 있는 작은 패키지로 만들었다는 점이다.

이런 작업을 반복하면 AI 결과물은 점점 일회성 산출물이 아니라, 내 작업 환경에 남는 도구가 된다.
